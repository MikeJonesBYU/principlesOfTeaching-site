Prompting Agents to Build

Team A's wireframe is four files. One data file holds all 53 blocks, every page is a filter over that file, and a built-in test mode later served as the instrument for the whole tree test. AI agents built it, and the prompts that got them there are unusually well documented. This tutorial walks through those prompts: what the instructor told the agents, what the agents got wrong anyway, and what you should say when you build yours.

The short version: the prompt that says "build it" is the easy part. The work happens before it (a spec you were interviewed into) and after it (someone other than the builder checking the result).

What is real on this page and what is not. Real: the instructor's prompts, quoted Verbatim with typos kept and cuts marked […]; the task packets the agents received; the verifier findings; and the two wireframes and their code, which really were built this way. Invented: the Timpanogos Shadows Ward, which was made up entirely by AI for this course; "Team A" and "Team B," which are fictional student teams (agents built both wireframes from the instructor's packets); and every tree-test participant and number, stamped Fictitious data. Prompts marked Reconstructed condense several real prompts into one. Nobody typed them as shown. Prompts marked Illustrative are weak examples written for this page.

1The whole workflow in one picture

Here is the sequence the instructor used. Each box is a separate prompt or a separate agent. The files along the bottom last longer than any one conversation, and later prompts point at them by name instead of repeating them.

You don't need a team of agents to use this. With a single chat assistant, you play the coordinator yourself, and you open a second, fresh chat as the verifier. Keeping those roles in separate conversations is the part that matters, not how many agents you run.

2What an agent assumes if you don't say

A coding agent knows a lot about code and nothing about your project. Anything you leave unsaid, it fills with the most common version of the thing. For a wireframe with instrumentation, the most common version looks a lot like Team B's, which was built on purpose to show these defaults.

You sayThe agent's likely defaultWhat to say instead
"a wireframe"A tidy styled page with default blue links and a second heading font "black/white/gray only, one system font, generic gray boxes; links black and underlined"
"two ways to browse"Two hand-built menus, each with its own copy of the items. The copies drift apart. "one data file; every page is a filter over it; no block hand-placed in HTML"
"record clicks"console.log, or an array that resets when the page changes (Team B's log does exactly this) the fields, where they're stored, the export format, and when logging stops
"a test mode"The happy path only: no give-up, and a reload loses the run the states: give up, reload mid-run, resume, end early
"make sure it works""I built it and it looks right" a self-check list you can audit, plus a check by someone other than the builder
(nothing about readers)Its own ids in every table: 006.title_number1, T02 who reads the output and what names they know

The instructor's founding prompt for the wireframe didn't ask for any code. It listed what he wanted, then asked the agent to ask him questions. Here it is, lightly trimmed.

Weak · Illustrative
Build me a wireframe website for our IA project with two navigation menus and click tracking. Make it look clean.
  • Every decision in it is the agent's to make, and it will make the common one (section 2).
  • "Clean" invites styling that the fidelity rule forbids.
  • Nothing tells the agent where the categories come from.
Stronger · Illustrative
Read spec.md and card-sort-analysis.md. Before writing any code, ask me questions ONE AT A TIME, multiple choice, until you can write a bullet-list spec. Then read the spec back to me and wait for my OK. Don't build yet.
  • It produces the spec before it produces code.
  • One question at a time means you actually read each one.
  • "Wait for my OK" gives you a checkpoint you control.

Rule of thumb. When none of the multiple-choice options fits, type your own answer. The options show you what the agent believes about your project. Clicking "Recommended" on each one approves those beliefs without reading them.

4Ask for a data contract, not a feature

"Two categorizations" is a feature. The instruction that made Team A's wireframe work was a contract: the exact shape of the data, and a rule about how pages may use it. This is from the task packet the builder received:

Coordinator → builder · packet W-A, build requirements 2–3 (excerpt) · Verbatim
2. **wireframe-data.js** — `window.WIREFRAME_DATA`, the single source: all 53 skills, each `{ id, name (verbatim from skills-data.js), url (real manual url), category, group, moment: [...] }`.
   […]
3. **Rendering rule (the exhibit)**: every page renders by selecting on attributes from WIREFRAME_DATA. No skill hand-placed in HTML anywhere.

Here is what the rule looks like in the finished code. It's short, because the contract did the design work:

prototypes/wireframe/team-a/app.jsfunction skillsInGroup(groupName) {
  return D.skills.filter(function (s) { return s.group === groupName; });
}
function skillsAt(momentKey) {
  return D.skills.filter(function (s) { return s.moment.indexOf(momentKey) !== -1; });
}

Make the rule checkable. "Single source" is easy to claim. The verifier checked it with a search: skill ids and manual URLs appear in app.js and index.html zero times. When you write an architectural rule, also write the test that would catch someone breaking it.

5Design the instrument for the next study

The test mode wasn't decoration. When the instructor specced the tree test, he said why the scenarios live inside the wireframe:

Instructor → coordinator · a typed answer in the tree-test interview · Verbatim
the ones built into the wireframe should be the ones they use for this test.  That's why they are in the wirframe.

So the build packet told the builder who would consume its output. That one sentence changes how an agent weighs every edge case:

Coordinator → builder · packet W-A, fiction framing (excerpt) · Verbatim
It is a REAL, working artifact. The next study (tree test) will run against it, and its bonus test mode becomes that study's instrument.

Name the fields, the storage, the export, and the isolation

Weak · Illustrative
Add click tracking and a test mode where users do tasks with a timer. Save the results.
  • Which clicks? Stored where? For how long?
  • Results in what format? Can they be exported?
  • What happens if someone gives up, or reloads?
Packet W-A, req. 5–6 (excerpt) · Verbatim
every navigation click appends `{t, from, to, label}`; persists in localStorage across sessions; a log view (#log) lists entries with Export JSON, Export CSV (blob download), copy-to-clipboard fallback, and a clear-log control.
[…]
reaching ANY L3 skill page ends the task, recording {taskId, endpointSkillId, expectedSkillId, seconds, path[]} […] While a test run is active, suppress/segregate normal #log recording so the two instruments don't cross-contaminate.

The test mode's flow is really a small state machine. If you draw it before you prompt, you can hand the agent the states and ask what happens at each edge. Here is the one that shipped. Its dashed parts were not in the first build, and a verifier found them missing (section 6).

Because the export format was specified exactly, it became the tree test's raw-data format without any translation. One row per task per run:

Team A's results export · header rowrunId,startedAt,finishedAt,taskId,scenario,expectedSkillId,endpointSkillId,asFiled,seconds,clicks,path

Contrast: Team B's log. It keeps clicks in an in-memory array on each page, shows a counter, and exports only the current page's clicks. Every navigation wipes it. The code works exactly as written; the design can't record a click sequence. That's what "record clicks" produces when nobody says where the clicks go.

6Builder, verifier, and the loop between them

The instructor set this up once, in a file (DELEGATION.md), before any wireframe existed. Three of its rules carry most of the weight:

  • "Separation of duties. The agent that built a thing never verifies it. Verifiers get a fresh context and are instructed to bias toward FAIL."
  • "One task, one packet, one agent."
  • "Never two agents on one file."

You don't need agent-definition files to follow them. With one chat assistant, open a new chat, paste it the packet and the builder's file list, and give it the verifier's instructions below.

The verifier's job: use the thing, fix nothing

The verifier packet restated the acceptance criteria and then said how to check them. Notice that the checks are actions:

Coordinator → verifier · VERIFY W-A, "How to verify" item 3 · Verbatim
Live-load from a /tmp copy (servers can't read ~/Documents): crawl both views for 53/53 reachability; click a skill from each view; verify end state + manual URL; exercise the click log (record, persist across reload, export JSON+CSV, clear); run at least 3 test-mode tasks including one give-up; reload mid-run to check persistence; check #results content and exports; confirm log/test segregation; console must stay clean.

The first build met every listed criterion. The verifier still returned PASS-WITH-NITS, and every nit came from actually using the app:

The clock showed "0.0s" at the moment of arrivalWatched the screen, not the code
"1 seconds"Read the output

Verifier returned PASS-WITH-NITS on W-A. The freeze rule means these get fixed NOW, before the tree test cites the artifact. Fix all four in companion/prototypes/wireframe/team-a/ (touch nothing else), self-verify live, and report back:
[…]
4. Mid-run reload: completed results persist (good) but the in-memory run is never rehydrated, so the participant silently lands back in normal browsing and their subsequent clicks leak into the normal click log. Since this artifact becomes the tree-test instrument, add graceful interruption handling: on boot, if a stored run is unfinished, show an explicit "your run was interrupted" state offering Resume (continue at the next task) or End run (mark it finished-incomplete). Either path must keep the log/test segregation guarantee intact.

Then a targeted re-verify: the same verifier checked only those four items plus a regression spot-check. It passed.

Pre-clear good deviations. The builder added a give-up button and a 1.1-second pause on the end state, neither of which was requested. The coordinator listed both in the verifier's packet under "Accepted deviations (do NOT flag these)." Ask builders to report deviations with reasons, then decide on them yourself before verification.

8Four pitfalls from this build

The coverage rule, caught late

The agent's spec summary said both views "must reach every block." The instructor approved it without noticing. Hours later a report boasted "53/53 in both views," the coordinator flagged the conflict with the approved spec, and the instructor gave the real rule:

Verbatim "Every block needs to be reachable in one organizational view of the blocks or another but not every block needs to be reachable in every organizational view."

Do this: when an agent reads your spec back, check every all, every, both, must, never. Those quantifiers are where a summary quietly changes your requirements.

Prose drifting from data

The tree-test data was generated by a script, and every table on the report page was correct. The verifier still returned FAIL: nine prose sentences contradicted the data, two of them in grader boxes claiming to have re-derived the number (for example, "five different blocks" where the log shows four) Fictitious data. The builder's own report had said it invented no numbers.

Do this: anything countable comes from code. In the prompt, say "every number in prose must come from the script's output," and have a different agent re-derive the numbers from the raw file.

Parallel agents, one file

At a later rung, two builders ran in parallel and one truncated a shared local config file to zero bytes. The file was untracked, so git couldn't bring it back, and the two agents then fought over it. At the same time, another session was editing the shared CSS.

Do this: give each agent a fenced list of allowed files. Shared files (config, stylesheets, the data file) belong to one owner, usually you.

The freeze rule

The moment a study runs on a build, that build freezes: the report cites it, so it can't change afterward. The verifier's nits therefore had to be fixed before the tree test, which is why the fix packet opens with "these get fixed NOW."

Do this: know which output becomes the next step's input, and settle it first. Once your tree test starts, changes go into the next prototype, not this one.

9Your template (for your domain)

Below is everything above in one prompt, with the ward taken out. Replace every [bracket]. It works best as the second message, after the agent has interviewed you (section 3) and you've approved the spec it read back.

Template · built from the real prompts above · Reconstructed 
Build a clickable WIREFRAME of our information architecture for [your domain, e.g. "a campus club's event archive"], plus the instrumentation we will use to tree-test it.

READ FIRST
- [card-sort-analysis.md]: our categories, labels, the pairs people always grouped, and the cards they split on
- [blocks.csv]: all [N] information blocks (id, exact title, source link)
- [spec.md]: the approved spec from our interview

WHO USES THIS NEXT
Our team runs a tree test with 10+ participants on this exact build. The results export IS our raw data. After the test starts, this build freezes.

FIDELITY
Black/white/gray only, one system font, generic gray boxes, no images. Links black and underlined (no default blue).

DATA CONTRACT (single source, multiple views)
- One data file holds every block: { id, title, url, [facet1: e.g. topic], [facet2: e.g. audience or time], ... }, plus the category and group lists and the 10 tasks.
- Every page is rendered by FILTERING that file on its attributes. No block is typed into HTML anywhere.
- View 1: by [facet1], at least 2 levels (category → group → block). View 2: by [facet2].
- Every block reachable in at least ONE view (not necessarily both).
- A leaf page names the block reached, with placeholder boxes.

CLICK LOG (always on)
- Each in-app navigation click appends { t (ISO UTC), from, to, label } to localStorage.
- A log view with Export JSON, Export CSV, a copy fallback, and Clear (with confirm).

TEST MODE (the tree-test instrument)
- Our 10 scenarios live in the data file, each with its expected block id. Scenarios use our users' words and never quote a category label. At least one probes our riskiest IA decision: [name it].
- Flow: shuffle per run → scenario card → OK starts the timer → participant starts at Home → reaching ANY leaf ends the task (clock frozen at arrival), or "I would give up" ends it with endpoint = null → "recorded" screen → next → summary.
- Per task record { taskId, expectedId, endpointId, correct, seconds, path[] }. Save the run after EVERY task.
- Results view with Export JSON + CSV, one row per task per run.
- During a run, clicks go ONLY to the run, never to the click log.
- Reload mid-run → a "run interrupted" screen with Resume / End run. No link may look clickable while it isn't.

DEFINITION OF DONE (run these, then report)
- A script that validates the data file: every block present exactly once, every block has its attributes, every task's expected id exists.
- Crawl both views and list any unreachable blocks.
- Complete a full 10-task run including one give-up and one mid-run reload; confirm both exports parse.
- Search the CSS for any non-gray color or second font. No console errors.

REPORT BACK
Files created; each requirement → met / not met, with evidence; the 10 tasks with expected blocks; every judgment call (e.g. where an ambiguous block went, and why); every deviation from this spec. Don't commit. We review first.

If you're running more than one agent

Coordinator add-on · Reconstructed 
You are the coordinator. Don't build it yourself.
(1) Turn the spec above into a TASK PACKET: read-first files, who uses the output next, requirements, data contract, allowed files, self-check, report format.
(2) Give the packet to ONE builder.
(3) When it reports, start a SEPARATE verifier with fresh context. Give it the packet and the builder's file list. Tell it to fix nothing, re-derive every number itself, exercise every state (reload mid-run, give up, click every link in every phase), and return PASS / FAIL / PASS-WITH-NITS with file:line evidence. List any builder deviations you accept, so the verifier doesn't flag them.
(4) Send failures back to the SAME builder. Then have the verifier re-check only what changed.
(5) Only you commit. Never let two agents edit the same file.

If you only have time for one paragraph

First message · Reconstructed 
I'm building a black-and-white clickable wireframe for my IA project from my card-sort results. Before writing any code, interview me one question at a time with multiple-choice options until you can write a bullet-list spec; then wait for my OK. Non-negotiables: one data file holds every information block with its attributes and every page is generated from it (single source, multiple views); two different categorizations grounded in my card sort; at least two levels; a persistent click log I can export as CSV; and a test mode that runs my 10 tree-test scenarios in random order with a timer, a give-up button, and exportable per-task results. Tell me how you'll verify each of those before you say you're done.
