CS 356 · Reading the card build (prototype v1, third build)

One Source, Many Views

The card build stores its 53 skills once and shows them through six routes, a search box, and a rack of facet chips. This tutorial shows how that is organized, then walks through adding a scheme the build does not have: the Ladder, organized by how ready a teacher is. Read the pictures first. The prose is deliberately short.

Three ideas from the course run underneath: Wurman's LATCH for choosing what to organize by, Ranganathan's facets for expecting several schemes at once, and the Polar Bear book's four systems for keeping organization, labels, navigation, and search apart.

1The whole idea in one picture

One file holds the 53 blocks and both ways of filing them. Two more files add to those blocks by pointing at their ids. Every screen is a route that selects from the same records and renders them through one card template.

2The four systems, found in the code

The Polar Bear book says a site has four systems that should be designed separately: organization, labeling, navigation, and search. In the card build each one has its own home, which is what lets a revision replace one without touching the others. The semantic build replaced search alone. The card build replaced labeling and the card template alone.

Spot the leak. cards/app.js carries a GROUP_LABELS table of fifteen group names, and the block page's "Filed under" trail reads from it. Those fifteen names already live in v1-data.js under groups[], one line away from groupBySlug(). Rename a group in the source and the block page lags behind every other screen. Two copies of a label is a labeling system with a fork in it. The fix is one line; it is exercise three in §8.

Four kinds of view

Look at how each route gets its arrangement. There are only four moves in the whole build.

RouteArranged byHowMove
#/c/:cat · #/g/:cat/:groupcategory → group → cardsFilters blocks whose filings[] hit the slug. No tree is stored; the tree is a query.derived at render
#/m/:keylesson moment → cards, sectioned by categoryFilters on moment[], then sections by each block's first filing.derived at render
#/tiles with countsCounts the same selections.derived at render
#/b/:idone block, every filing, the first moveOne id from the URL, joined with cards[id].selection + overlay
#/find?q=&f=ranked cards, then narrowedLiteral weights + lookups in S.terms; chips are counts over the results on screen.derived at build + derived at render
#/logtimeReads localStorage.instrument
Derived at render = the field you select on is already in the source. A few lines in a view.
Derived at build = computed once by a tool, checked in as a file, only looked up in the browser.
Authored overlay = a new file that adds meaning under ids. Never copies content.
Selection = ids carried in the URL. The view is whatever those ids resolve to.

In Polar Bear vocabulary those are structures. The scheme is the shared characteristic you group by. Categories and groups are a task scheme ("start with the problem you are having") in a hierarchy, but a polyhierarchy: filings[] lets a block sit in two branches. Moments are a time scheme in a database structure: a tag, filtered flat. The book calls those top-down and bottom-up. The card build runs both over one record set. Scheme is a content decision. Structure is a code decision. Decide them separately, and in that order.

Notice the second column. The build ranks its own labels by where they came from: study evidence above the manual above the author's ear. That ordering is a labeling decision, written down once, and both the card and the search obey it.

4Same 53 dots, regrouped

Each dot is one block, colored by its home category (the first filing). Switch the grouping. The dots never change; only the boxes around them do. That is the entire lesson.

One id, many facets

Ranganathan's lasting idea is not the five letters of PMEST. It is that one thing is classified on several independent facets at once, and the class is composed at lookup, never stored as one big tree. The card build already does this. Each facet is a file, or a field, and the id composes them.

5The new scheme: the Ladder

Start with LATCH

Wurman's five hat racks are the fastest way to find a scheme you do not have yet. Walk the letters against the 53 blocks and note which ones the card build already fills.

Organize by…In the card buildExact or ambiguous?Status

Hierarchyhow much: readiness of the teachernothing yetambiguous→ the Ladder

Three things fall out of the table. Exact schemes (L, A, T) are usually derived views: the field is already in the source and a sort does the work. Ambiguous schemes (C, H) are authored, so they become overlays. And the build already has a small H: the prep chip is a two-step magnitude scale about materials. The Ladder is a four-step magnitude scale about the teacher. Wurman's "hierarchy" means ordering by magnitude, not a tree. The category view is a tree; the Ladder is a flat, ordered list. Same word, two ideas.

Every existing way in asks what a block is about or when it is used. The Ladder asks how ready a teacher has to be to try it. A first-week volunteer and a ten-year veteran should not get the same list.

1
First SundaysDoable this week with no preparation and little risk. "Communicate that students are needed."
2
Building habitsNeeds preparation during the week. Becomes a routine. "Create open-ended search questions."
3
Reading the roomNeeds in-the-moment judgment or doctrinal care. "Respond without speculation."
4
Holding steadySustained charity under strain. "Testify of God's love when it is hard to feel it."

7Rules to carry to your own project

Ids are addresses. Give every record one. Never rename it. Routes, overlays, logs, indexes, and other builds all meet at the id.
Overlays point; they do not copy. If a name appears in two files, one of them is wrong. §2 found one.
Load data by reference; copy only views. The revision line's own rule. A new build may fork app.js. It may never fork v1-data.js.
Keys and words are separate. Slugs in routes and logs, names on screen. The Polar Bear book treats labeling as its own system for exactly this reason.
Expect more schemes than one. Ranganathan's point. Store each facet on its own, compose at lookup, and the next scheme costs one file.
Walk LATCH before inventing. It tells you which schemes are exact (derive them) and which are ambiguous (author them), and which the build already has.
Write the provenance into the data. Harvested, authored, derived, generated. The search weights and the card lead read it. So does the grader.

8Try it

  • Derived (A): add #/az, all 53 blocks by name. No new file. Which move from §3 is this, and where does the sort live?
  • Overlay, many-to-many (C, audience): tag blocks by audience: children, youth, adults. Write the validator before the data. What does "missing" mean here?
  • Repair (labeling): delete GROUP_LABELS from app.js and read the name through groupBySlug(). What else in the block page was quietly depending on it?
  • Make the convention explicit: the moment view sections by filings[0]. Nothing in the data says the first filing is the home filing. Add a field, or a comment, and say which you chose.
  • Compose (facets): put the rung on the card as a chip, then look at a two-up grid on a phone. Keep it or take it out, and tag the decision evidence or conviction.
  • Derived at build (T → H): instead of terms[], add the rung blurbs to the corpus and rebuild the semantic index. What new file appears, and what does the next build have to load?
